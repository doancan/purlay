# D-345. The decision record is one file per decision, indexed by category, and a new one is made by a command

**Decided (the owner, 2026-11-26).** `DECISIONS.md` had grown to 16,788 lines and 343 decisions in one file. Nobody
could read it, every pull request that recorded a decision edited the same end of the same file, and the owner asked
for it to be divided, put into categories and given a way of working that does not end in the same place again.

**What changed.**

- Each decision is `docs/decisions/<category>/D-<n>-<a-few-words>.md`, headed `# D-<n>. <title>`. Its words are the
  ones the single file had, checked character for character when they were moved; only the heading level changed.
  The nine categories (product, architecture, data, security, web-ui, mobile, operations, engineering, integrations)
  were assigned by what each decision is mainly about, by one pass and an independent review of it.
- The open questions are `docs/decisions/open-questions.md`. `docs/DECISIONS.md` stays as a short page that sends a
  reader there, so the links and citations that name it still arrive somewhere true.
- `docs/decisions/README.md` says how to find and record a decision; its index, a table per category with the day
  and the decisions that amended each one, is generated by `bun run decisions:index` from the files.
- `bun run decision:new <category> <title>` takes the next number and writes the file from `_template.md`, which asks
  for what every decision owes: the reason, what was rejected, the cost of reversing. `bun run module:new` writes a new
  module's decision the same way, as a template file in `architecture/`.
- `bun run check:docs` reads the files as the one record they were, so every rule it held still holds (an amendment's
  note pointing back, a cost of reversing from D-250, no gap or repeat in the numbers, nothing filed among the open
  questions, nothing uncited), and adds the ones a directory needs: a file's name and heading agree, its category is
  one of the nine, no two files hold one number, and the index is what the files say.

**Rejected.**

- A file per category (nine files of one to three thousand lines): smaller, but still one file every pull request in
  a category edits, and still too long to read.
- Renumbering, or numbering per category: thousands of citations in code and documents name a decision by number.
  The number stays the name; the category is only where the file lives, and moving it is free.
- Writing the index by hand: it would drift from the files on the first decision somebody forgot to list.

**Cost of reversing.** Moderate: concatenating the files in number order rebuilds the single document exactly (the
move was checked that way), and `check-docs.py`, the three tests that read a decision's text, `module:new` and the
contributing documents would go back to naming one file.
