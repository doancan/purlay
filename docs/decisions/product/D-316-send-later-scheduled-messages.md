# D-316. Send later: the web holds nothing itself, and reads the one fact it needs from the session

*Amended by D-319: "In 1 hour" says the clock time it comes to.*

**Decided by the owner, 2026-11-18.** The server already holds a scheduled message until its time (`PUT` and `DELETE /api/channels/:channelId/scheduled/:scheduledId`, `GET /api/workspaces/:workspaceId/scheduled`, `capabilities.scheduledMessages`, API.md "Scheduled messages"). The web client now uses it, and keeps nothing of its own: no copy of the list on the device, no timer, no queue.

**The button.** Beside Send, in a channel's box and a thread's, a *Send later* button opens a menu: *In 1 hour*, *Tomorrow at 09:00*, *Monday at 09:00* and *Pick date and time…*. Monday is left out on a Sunday, when it is tomorrow, and on a Monday, when the word would read as today. The times are wall-clock times in the viewer's zone, turned into instants by the formatters (`instantOf`, shared with the reminders' presets, D-315), which know the zone's clock changes: *Tomorrow at 09:00* across the night the clocks move is still nine o'clock, and *In 1 hour* is still an hour. They are worked out when the menu opens and again when one is chosen, from the system clock, so a test names the instant. The dialog is the browser's own `datetime-local` field, from a minute to 365 days ahead, which says in place what is wrong with a time and what a good one means; it is loaded when first wanted.

**What is scheduled is what a send would send.** The box is read as a send reads it, and refused for the same reasons by the same code (a file that failed, over the limit, a character the contract refuses, an `@here` the channel does not allow); what a schedule adds is that it will not wait for an upload (a send does) and will not take a `/command`. Words and ready files go in one `PUT` under a UUIDv7 chosen here, kept while the same words, files and time are asked again after a failure that did not say whether it landed. On success the box and its draft are emptied as a send empties them, and a toast says when, with *View scheduled*. On failure — the limit, a refused time, no connection — the words and files stay and the reason is said under the box. It is never disabled while sends wait for the network: it needs the network itself, and says so.

**The list.** A third tab in Drafts and sent, *Scheduled*, with a count: where, when (today or tomorrow in words), the words, the files, and for one the server could not send, *Failed:* and a reason from the code the server wrote (the channel is gone, you are no longer in it, only admins post there now, the message you replied to is gone, a file is gone, no access). It is read when the screen opens, when the tab opens and when the window is focused, because the server has no push for it. *Cancel* asks the server and offers *Undo*, which asks for the same message again under the same id as long as that is still possible. *Edit* writes the words into that place's draft (under any words already there), then cancels, then opens the box: if the device cannot keep the draft, nothing is cancelled, and if the cancel is refused, the draft is put back. A scheduled message's files are not carried into a draft, because a draft is text; the toast says so.

**How the web knows the server can do this.** It does not call `GET /api/client`, which D-248 keeps for the native clients and charges to the address with sign-in. The server advertises `scheduledMessages` "only where chat runs", and the session says what the server runs, so the web reads the flag as *chat runs* (`useRunsIfAny('chat')`, the same read the reminders make, D-315). The web and the server it talks to are one build, so no older server is behind a newer page.

**Rejected.** Keeping scheduled messages in the browser and sending them at their time: it needs the page open, which is what scheduling is for not needing, and a second device would not see them. Calling `GET /api/client` once per session for the flag: D-248's reason, one more request from every page load against the budget people sign in with. Adding `capabilities` to `GET /api/me`: a contract change on the server for a flag that follows a module the same response already names; it is the way to go if the flag ever stops following chat. The product's own date field (D-247) with a separate time input: two controls and two sets of messages for what the browser's one field says, with a native picker on a phone; D-247's complaint of the browser's date input was a field with no minimum to explain, which this dialog gives in words. A preset for *Monday* every day: on a Monday it would read as the day it is. Carrying files back into a draft: drafts are text on this device by D-41, and holding files there is another store. Offering a time less than a minute away: the server's floor is five seconds, but a time a minute away is the least a person can mean by *later*, and the typed field has nothing finer than a minute.

**Cost of reversing.** Delete the button, the tab and the three endpoint methods. Messages already scheduled stay on the server and are delivered; the native client lists them. No schema, no stored format on the device, no contract change.
