# D-324. Send now is the scheduler's delivery, asked for early — builds on D-316

**Decided by the owner, 2026-11-20**, from the UX review of v0.7.1 (#1478). The Scheduled list offered Edit and Cancel but no way to send a message that was ready before its time. The client could not do it honestly with what the server had: rescheduling needs a time at least five seconds ahead and the server claims due rows every 15 seconds, so "now" would be "in up to twenty seconds"; and sending an ordinary message and then cancelling the schedule is two requests, which leave a duplicate when the second fails or the scheduler runs between them.

**What changes.** `POST /api/channels/:channelId/scheduled/:scheduledId/send` sends the caller's own pending or failed scheduled message at once and answers the `Message`. It runs the scheduler's own delivery (`deliverRow` in `features/chat/scheduled/delivery.ts`, which the scheduler now calls too): the channel, the membership and the reply target are checked again, the reserved files are let go and linked, the message's UUIDv7 is made at that moment, and the row is marked sent with the message's id in the same transaction. The row is locked with `FOR UPDATE` and waited for, where the scheduler uses `SKIP LOCKED`: whichever commits second finds it sent, so the scheduler skips it and *Send now* answers `409 SCHEDULED_MESSAGE_SENT`. A double press, two devices and a race with the scheduler each make one message, and asking again after a lost answer is safe. A refusal (no longer in the channel, the root deleted, only admins post) is written on the row as the scheduler writes it, `failed` with its code, and is the response. The caller's live session is the authority, as for any send; the scheduler's check of the session that scheduled it (the deferred source of D-310) is not needed when the person is there. Another person's, another channel's or an unknown id is `404 SCHEDULED_MESSAGE_NOT_FOUND`, a channel the caller cannot see `404 CHANNEL_NOT_FOUND`.

**The web.** A *Send now* button beside Edit and Cancel, with the send glyph. The row leaves the list at once; on success a toast says where it went (*Sent in ops.*) and the Sent tab is read again; *already sent* is said and the row stays gone; any other refusal puts the row back, says why in the words a failed row uses, and the list is read again so the row shows it as failed.

**Rejected.** Doing it in the client as a send and a cancel: two requests, and a duplicate whenever the second fails. A `PUT` with a `sendAt` of now: the five-second floor and the fifteen-second tick, and a person pressing *now* would wait for a timer. Skipping a locked row in *Send now* as the scheduler does: the press would answer before knowing whether the message went. Answering the updated `ScheduledMessage`: the client has nothing to do with a sent row but drop it, while the message is what a client that missed the socket frame can show.

**Cost of reversing.** Remove the route, its endpoint entry, the client method and the button; no schema, stored format or frame changed, and the scheduler's delivery is the same code it was.
