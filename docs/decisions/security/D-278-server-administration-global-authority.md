# D-278. Server administration is global metadata authority, independent of a workspace — builds on D-179, D-233, D-250

**Numbering.** The administration migrations retain their original branch-local D-277 annotations for checksum compatibility. This record is D-278 after main assigned D-277 to the web module boundaries; no applied SQL was rewritten.

**Context.** The server page configures sign-in and mail but gives operators no inventory or operational view. Its workspace route also prevents an administrator without membership from reaching administration. Server metadata authority must not imply access to private conversations.

**Decision.**

1. A standalone `/server` console uses the existing session and server-administrator guard, never a fabricated workspace context. The legacy workspace entry leads to this console. Core administration remains present when optional modules are disabled.
2. Additive `/api/server` APIs return bounded keyset inventories of users, workspace metadata and the server audit trail. Workspaces include owner previews, counts, retention policy and storage including pending uploads. Exact byte totals cross as decimal strings. They expose neither message content nor credentials, raw operational errors or session tokens. Every route guards before parsing; failures remain no-store. Audit actions have English/Turkish labels with a raw-name fallback for newer actions; a searchable paginated person picker and entry actors select the same id filter, including former accounts. CSV/NDJSON downloads use the same filters and metadata, reuse D-222 CSV protection, and stream 100 rows at a time with no read-ahead or held connection between pages. Current administrator authority is rechecked before each chunk; cancellation stops subsequent reads. `server.audit_export_requested` records the attempt before bytes, without implying successful delivery. Fetching every row into the browser and carrying raw operational values into the export were rejected.
3. Administrator changes serialize on one transaction advisory lock before any account lock, then recheck the actor. At least one active administrator remains. Grants require an active account and verified email. Session revocations and quota changes commit with server audit entries; session-ended publications follow the commit. Quota changes reuse the operator service, preserve content and may set a limit below current usage.
4. Overview readiness comes from the actual readiness service. Configured storage/push/shared-state are described as configuration, not proven health. Job status uses the deployed composition's catalogue and the CLI's staleness rule. Unreported backups and unverified restoration must stay explicit; no invented success state or browser restore.
5. Existing provider configuration remains the supported live-settings seam. Infrastructure credentials and the deployment URL stay operator-managed. New admission policies must be enforced at the identity/session boundary, default off for old deployments, and cannot be merely UI switches.

**Cost of reversing.** Remove the additive routes and console. Existing accounts, quotas, settings and append-only audit records remain valid; there is no content migration.

**Batch approval (D-278 continued).** An administrator confirms up to 50 explicit account ids, with one transaction and audit entry per newly approved account. Each item rechecks current administration authority and the account state under the existing session/account locks. A pending-only precondition prevents a concurrently denied account from being admitted; already-approved accounts are idempotent. Replies preserve input order and distinguish approved, refused, unconfirmed and not-processed items. Cancellation/authority loss stops unstarted work, and an unexpected database failure is unconfirmed rather than a claim that nothing committed. Selection survives pages within one filter, resets on filter changes, and unsuccessful selections remain available for explicit retry. Approval never adds membership or administrator rights and never substitutes for email verification. An all-or-nothing bulk transaction and automatic write replay were rejected: one unavailable account must not undo others, and a lost reply cannot prove a write failed.

**Admission and identity (D-278 continued).** Policy applies at new-account creation, not to old accounts: every existing row defaults to approved. Exact, normalized domains have no wildcard/subdomain inheritance; invitation passports do not bypass policy. A domain-restricted new account needs verified email. The auth library writes approval fields from policy, never client input. Pending/denied sessions are identity-only: only their own admission status and sign-out are reachable; common HTTP/session and realtime write guards refuse application access. Approval does not grant workspace membership or bypass MFA. Denial revokes sessions and is audited; turning approval off does not admit the waiting list. Partial preference patches serialize with role/provider changes and preserve concurrent changes to other fields. Public instance info is limited to name, support and joining requirements. Infrastructure URL remains operator-managed.

**Operational evidence (D-278 continued).** Backup status is a bounded, validated file source mounted read-only, produced after the actual operator backup/restore scripts succeed. Dockhand publishes database-only evidence into a separate metadata volume, not the archives. Artifact SHA-256 and scope bind a restore check to the backup it checked; checksum/SQL/table-count verification is distinguished from application-level recovery. No source, no receipt, invalid evidence, stale evidence and no restore check remain explicit states. Database content is not changed to report backup completion, so a receipt cannot invalidate source-versus-restored database comparison.

**Problem summary (D-278 continued).** The overview reuses the guarded overview, job and backup reports to identify failed exports, jobs that failed or never succeeded or are overdue, and every non-current backup evidence state. Freshness remains the server's existing policy: the job reporter's rule and each validated backup receipt's `maxAgeSeconds`, not a browser clock or a new threshold. Problems link to Data or Operations, and affected jobs expand by name. Each source retains its reported check time. Pending or failed reads prevent an all-clear, preserve available results, identify the unavailable source and offer an independent retry; Refresh asks all three sources again. A clean result is scoped to these reports and is not a claim of verified recovery or overall infrastructure health. This needs no optional module, new API, migration or operator secret.
