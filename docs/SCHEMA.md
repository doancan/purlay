# Purlay — Data Model (`SCHEMA.md`)

> Authority: `DECISIONS.md` explains *why*. This file is the normative definition of *what is
> stored*. If SQL here and prose elsewhere disagree, this file wins.
> Target: the PostgreSQL major named in `ARCHITECTURE.md` §2, which owns every version in the
> stack. Repeating it here is how one copy goes stale (D-20).
> Identifier columns carry an explicit `COLLATE "C"` so uniqueness never depends on the locale the
> server was provisioned with (D-40).

---

## 1. Storage Rules

1. **Tenant isolation is structural.** Every workspace-scoped table carries an indexed
   `workspace_id` (a test checks that every foreign key has an index, §6.2), and every query against those
   tables filters on it. There are no exceptions
   — which is precisely what makes the rule enforceable. (D-3, D-6)
2. **Content is soft-deleted, and soft deletion never cascades.** `deleted_at` is set and
   `content` is replaced with a tombstone. A deleted parent message does not take its thread
   with it. Hard deletion happens only in an operator-run purge. (D-9)
3. **`messages.id` is a UUIDv7 generated by the application.** The column has no default, so an
   insert that forgets to supply one fails loudly rather than silently producing an unorderable
   row. Every other table uses `gen_random_uuid()`. (D-8)
4. **Counters that appear in list views are denormalized.** Unread counts and thread reply
   counts are maintained columns, never `COUNT(*)` subqueries in a sidebar render. (D-13)
5. **Secrets are never stored in plaintext.** Session tokens are stored as SHA-256 hashes;
   third-party access tokens are encrypted with AES-256-GCM at the application layer.
   (D-11, D-23, D-39)
6. **Identifiers collate deterministically.** `channels.name`, `workspaces.slug`,
   `users.username` and `users.email` carry an explicit `COLLATE "C"`, so uniqueness and case
   folding never depend on the locale the server was provisioned with. (D-40)

## 3. Identity

### 3.1. `users`

Global account. Not workspace-scoped: one identity spans workspaces. (D-3)

```sql
CREATE TABLE users (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),

    -- Nullable for two reasons: Phase 2 magic-link accounts have no GitHub identity (D-11),
    -- and erasure clears this column so a returning person gets a new account rather than
    -- resurrecting the one they asked to have removed (D-38). UNIQUE permits many NULLs.
    github_id     BIGINT UNIQUE,

    -- The login as GitHub last gave it, written on every GitHub sign-in (and on linking it to an account made by email, D-179 §5) and
    -- taken from any other account still holding it; NULL for an email link's account that has not
    -- connected GitHub, and after erasure. What
    -- WORKSPACE_CREATORS is matched against — never `username`, which takes a `-N` or an
    -- address. TEXT: GitHub's value, compared as given. Not unique: two sign-ins at once may
    -- briefly share it. (D-169)
    github_login  TEXT COLLATE "C",

    -- When GitHub was joined to an account made by an email link — from a session signed in as it
    -- (D-176), or by a GitHub sign-in on its verified address (D-179 §5); NULL for an account GitHub
    -- made, one that has not been joined, and after erasure. Tells the two apart once both have a
    -- github_id: the first keeps its email link and its own names.
    github_connected_at TIMESTAMPTZ,

    -- Whether the address is one a provider vouched for, or a link sent to it was followed. Better Auth
    -- reads it: an address that is not verified is never linked to by one that is, and an invitation is
    -- accepted only by an account whose address is. FALSE until something says so. (D-179, 0047)
    email_verified BOOLEAN NOT NULL DEFAULT FALSE,

    -- Who may change the server's settings. Ours and not the library's: its Admin plugin is not
    -- installed. FALSE for everyone until the person who sets the server up is made one. (D-179, 0047)
    is_server_admin BOOLEAN NOT NULL DEFAULT FALSE,

    -- Suspended by the server's administrator (D-233): the account starts and resolves no session, and keeps
    -- its history and its name. NULL is an account in use. (0065)
    suspended_at TIMESTAMPTZ,

    -- Quiet hours (D-234): minutes after midnight on the profile's clock (`time_zone`), and the days a window
    -- starts on, a bit each from Sunday (1) to Saturday (64). All NULL, or all set with two different ends
    -- (`users_quiet_hours_whole`). `from` later than `to` runs past midnight. (0066)
    quiet_from SMALLINT,
    quiet_to   SMALLINT,
    quiet_days SMALLINT,

    -- Whether a password sign-in asks for a code from an authenticator app too (D-236): set by the sign-in
    -- library once a first code was right, cleared when it is turned off, by the server's reset and by erasure.
    -- Its key is in `two_factors`. (0067)
    two_factor_enabled BOOLEAN NOT NULL DEFAULT FALSE,

    -- When the person asked to be emailed about the mentions and direct messages they leave unread (D-240);
    -- NULL is off, as every account starts. Only what they were told since is ever mailed. (0069)
    missed_mail_since TIMESTAMPTZ,

    -- The stable identity anchor across auth methods. Normalised to lowercase ASCII by the
    -- application; COLLATE "C" so comparison is byte-wise and identical everywhere. (D-40)
    email         TEXT COLLATE "C" NOT NULL UNIQUE,

    -- 39 characters is GitHub's maximum username length.
    username      VARCHAR(39) COLLATE "C" NOT NULL UNIQUE,
    display_name  VARCHAR(128) NOT NULL,
    avatar_url    TEXT,

    -- Best-effort, updated lazily. Live presence is in-memory and never persisted. (D-7)
    last_seen_at  TIMESTAMPTZ,

    -- The language this person's notifications are written in, set by their client (D-41, D-126).
    locale        TEXT NOT NULL DEFAULT 'en' CONSTRAINT users_locale_known CHECK (locale IN ('en', 'tr')),

    -- What a person says about themselves (D-131): each NULL until set, never blank. The time zone
    -- is an IANA name the service checks against its runtime; the database holds its length only.
    title         VARCHAR(80),
    time_zone     VARCHAR(64),
    status_text   VARCHAR(100),

    created_at    TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    updated_at    TIMESTAMPTZ  NOT NULL DEFAULT NOW(),

    -- Soft delete, so authorship on historical messages survives. (D-22)
    deleted_at    TIMESTAMPTZ,

    CONSTRAINT users_quiet_hours_whole CHECK (
        (quiet_from IS NULL AND quiet_to IS NULL AND quiet_days IS NULL)
        OR (
            quiet_from BETWEEN 0 AND 1439
            AND quiet_to BETWEEN 0 AND 1439
            AND quiet_from <> quiet_to
            AND quiet_days BETWEEN 1 AND 127
        )
    ),
    CONSTRAINT users_profile_not_blank CHECK (
        (title IS NULL OR btrim(title) <> '')
        AND (time_zone IS NULL OR btrim(time_zone) <> '')
        AND (status_text IS NULL OR btrim(status_text) <> '')
    )
);

-- A sign-in takes its login from any other account holding it, found by the login as compared. (D-169)
CREATE INDEX idx_users_github_login ON users (lower(github_login)) WHERE github_login IS NOT NULL;
```

### 3.2. `sessions`

Opaque bearer token in an `HttpOnly` cookie, validated against this table on every request and
on every WebSocket upgrade. Chosen over stateless JWT for revocability. (D-11)

*Amended 2026-10-21 by D-179:* Better Auth reads and writes this table through a mapping of its fields
onto these columns (`createAuth`); nothing about the columns changed. It deletes a session's row when
the session ends, whether by sign-out or by revoking it, and so does every way Purlay ends one
(`modules/auth/sessions.ts`), so nothing writes `revoked_at` any more and nothing reads it but the purge
below, which still removes a row that has one. The column and its index stay, with no migration: a row
that carries it can only be from before D-179, and it cannot authenticate anyone (the cookie is the library's
now, signed under its secret). `token_hash` still holds
only the SHA-256 of the token: the library is handed a database handle whose plugin
(`sessionTokenHashing`, `@purlay/db`) hashes every value bound to it.

```sql
CREATE TABLE sessions (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id      UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,

    -- SHA-256 of the opaque token. The raw token exists only in the user's cookie:
    -- a database dump therefore does not hand over live sessions.
    token_hash   TEXT NOT NULL UNIQUE,

    user_agent   TEXT,
    ip_address   INET,
    -- What a device list names the session by (D-193): the native application's device name, null for a browser.
    device_name  TEXT,

    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    last_used_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    expires_at   TIMESTAMPTZ NOT NULL,
    revoked_at   TIMESTAMPTZ,

    -- Bounded as the request is (`NATIVE_DEVICE_NAME_PATTERN`). Added by 0057. (D-193)
    CONSTRAINT sessions_device_name_bounded
        CHECK (device_name IS NULL OR char_length(device_name) BETWEEN 1 AND 64)
);

CREATE INDEX idx_sessions_user    ON sessions (user_id);
CREATE INDEX idx_sessions_expiry  ON sessions (expires_at) WHERE revoked_at IS NULL;
CREATE INDEX idx_sessions_revoked ON sessions (revoked_at) WHERE revoked_at IS NOT NULL;
```

`ip_address` is the client address at sign-in (the socket's peer, or the proxy-reported one under `TRUST_PROXY`; null if unknown). It is personal data: erasure nulls it with the session (D-27, D-81).

`device_name` is the name the person's Mac gave itself, written when the native application's code is spent (D-191) and read only back to that person (D-193); it is bounded as the request is (`NATIVE_DEVICE_NAME_PATTERN`).

`last_used_at` is refreshed at most once an hour, not on every request: this table is read on every HTTP request and every socket upgrade, and a write there would be a write on the hottest path in the system. (D-60) Where the server signs out an unused session, at most every five minutes instead, and also when the page says the person is using it (the socket's `ACTIVE`), since it is then what the idle timeout is judged by; a session is ended when `last_used_at` plus the timeout, or `created_at` plus the maximum age, has passed, and its row is deleted (D-244).

Expired rows are not kept: `purgeDeadSessions` removes them in bounded batches, called by the scheduler (#71), and with them any row from before D-179 that still carries `revoked_at`. (D-87)

### 3.2.1. `accounts`, `verifications` and `rate_limits`

What Better Auth keeps beside `users` and `sessions` (D-179, 0047). Its schema check compares the
database with what it expects and refuses to run on a difference, so these are its core schema under
Purlay's names.

```sql
-- One row for each way a person signs in: a provider's account, or a credential account's password.
CREATE TABLE accounts (
    id                       UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id                  UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    provider_id              TEXT NOT NULL,   -- 'github', or 'credential' for a password
    account_id               TEXT NOT NULL,   -- the provider's id for the person; the user's id for 'credential'
    -- Present because the schema check demands them; never written: a hook of `createAuth` nulls them, as
    -- Purlay never calls GitHub on a person's behalf and a stored token would be a credential kept for nothing. (D-179)
    access_token             TEXT,
    refresh_token            TEXT,
    id_token                 TEXT,
    access_token_expires_at  TIMESTAMPTZ,
    refresh_token_expires_at TIMESTAMPTZ,
    scope                    TEXT,
    password                 TEXT,            -- the hash, for a credential account only
    created_at               TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at               TIMESTAMPTZ NOT NULL DEFAULT NOW(),

    UNIQUE (provider_id, account_id)          -- a provider's account is one row
);

CREATE INDEX idx_accounts_user ON accounts (user_id);

-- Short-lived tokens the library issues, a sign-in link among them.
CREATE TABLE verifications (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    identifier  TEXT NOT NULL,
    value       TEXT NOT NULL,
    expires_at  TIMESTAMPTZ NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE INDEX idx_verifications_identifier ON verifications (identifier);

-- Its counters for sign-in attempts, here so a restart does not hand every attempt back and every
-- process counts the same ones.
CREATE TABLE rate_limits (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    key           TEXT NOT NULL UNIQUE,
    count         INTEGER NOT NULL,
    last_request  BIGINT NOT NULL             -- milliseconds since the epoch
);
```

Deleting a user deletes its `accounts`. No row of `verifications` is keyed by a person, and one of
`rate_limits` is, for a day: an inviter's count of invitation e-mails (`purlay:invite-mail:inviter:` and
their id; the workspace's is `…:workspace:` and its id), which an erasure deletes. Both are short-lived: a sign-in link's `identifier` is `magic-link:` and its token's digest, and its
`value` the address as JSON, which is how erasure finds it; a reset's `value` is the user's id. The
library's `rate_limits` rows are a client address and a path; Purlay's own sign-in-link counters are
`purlay:sign-in-link:client:<digest>`, `purlay:sign-in-link:address:<digest>` and, per client,
`purlay:sign-in-link:address:<digest>:client:<digest>` (D-231 §2), with `last_request` the moment the hour
closes (D-179 §3), and an erasure deletes every one under its address's prefix. The wrong passwords counted against a client are
`purlay:password:address:<digest>:client:<digest>` and `purlay:password:client:<digest>`, the client being its network (an IPv4 address or an IPv6 /64), their window
fifteen minutes (D-179 §4); an erasure deletes every one under its address's prefix. A password lives
only in `accounts.password`, on the row whose `provider_id` is `credential` and whose `account_id` is the
user's own id, as the library's scrypt (`<salt hex>:<key hex>`) — never the password itself.

### 3.2.2. `two_factors`

Two-step verification for an account with a password (D-236, 0067): the sign-in library's two-factor plugin
keeps a row here per person who began to turn it on, under Purlay's names (`createAuth`).

- **Sealed, never as shown.** `secret` is the authenticator app's key and `backup_codes` the unused backup
  codes as JSON, each encrypted by the library under the server's derived secret (`deriveAuthSecret`). A copy of
  the table signs nobody in.
- **On only once a code was right.** `verified` is FALSE from the moment the key is made until the first right
  code from the app, which also sets `users.two_factor_enabled`; a row that is not verified asks nothing of a
  sign-in, and beginning again replaces its key.
- **The lockout is the library's.** `failed_verification_count` counts wrong codes in a row at sign-in, across
  challenges and kinds of code; at ten, `locked_until` is fifteen minutes on, and a right code resets both.
- **One row a person** (`two_factors_user_key`), `ON DELETE CASCADE`; turning it off deletes the row, and so do
  erasure and the server's `admin:reset-password`.

The challenge a right password opens is a row of `verifications` (`2fa-` and a random id, its `value` the user's
id, with a `2fa-attempts-` row beside it counting that challenge's codes), for ten minutes. Instance-wide; never
exported.

```sql
CREATE TABLE two_factors (
    id                         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id                    UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    secret                     TEXT NOT NULL,
    backup_codes               TEXT NOT NULL,
    verified                   BOOLEAN NOT NULL DEFAULT FALSE,
    failed_verification_count  INTEGER NOT NULL DEFAULT 0,
    locked_until               TIMESTAMPTZ,

    CONSTRAINT two_factors_user_key UNIQUE (user_id),
    CONSTRAINT two_factors_failures_counted CHECK (failed_verification_count >= 0)
);
```

### 3.3. `push_subscriptions` and `users.locale`

A person's devices that are told, by Web Push, of what needs them while Purlay is closed (#78, D-126),
and the language the server writes those notices in (D-41).

```sql
CREATE TABLE push_subscriptions (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id     UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    -- The session it was made in: signing out deletes it, and a push needs the session live.
    session_id  UUID NOT NULL REFERENCES sessions(id) ON DELETE CASCADE,
    -- The push service's address for this browser; unique across people, so a browser signed
    -- into another account moves to it rather than telling two.
    endpoint    TEXT NOT NULL UNIQUE,
    p256dh      TEXT NOT NULL,   -- the browser's P-256 point, validated as one on the way in
    auth        TEXT NOT NULL,   -- its 16-byte secret (RFC 8291)
    -- The application-server key it was made with: after the operator changes it, inert.
    server_key  TEXT NOT NULL,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
    failures    INTEGER NOT NULL DEFAULT 0,   -- deliveries in a row the push service did not take

    CONSTRAINT push_subscriptions_endpoint_is_https CHECK (endpoint LIKE 'https://%'),
    CONSTRAINT push_subscriptions_endpoint_bounded CHECK (length(endpoint) <= 2048),
    CONSTRAINT push_subscriptions_failures_counted CHECK (failures >= 0)
);

CREATE INDEX idx_push_subscriptions_user    ON push_subscriptions (user_id, created_at);
CREATE INDEX idx_push_subscriptions_session ON push_subscriptions (session_id);
```

At most 20 devices a person, the least recently subscribed dropped when a twenty-first subscribes
(subscribing again sets `created_at`). A row moves to another person only when they send its keys
as well as its endpoint. A session's rows go when its row is deleted (sign-out, sign out everywhere,
expiry swept by `purgeDeadSessions`): the foreign key takes them with it, in the same transaction.
The endpoint and both keys are a person's: never logged (`ARCHITECTURE.md` §10).

### 3.4. `email_sign_ins`

**Dropped by migration 0048 (D-179).** Every message sent to sign in by email (migration 0038, D-138)
was a row here: a link, or a word that the address signs in with GitHub. A link is Better Auth's
magic link now, kept in `verifications` (§3.2.1) and swept by `sweep:email-sign-ins` a day after it
expires; the per-address count is a counter of Purlay's in `rate_limits`. Nothing wrote this table
after the move, so it went rather than stay a second home for the same fact.

## 4. Workspaces & Membership

### 4.1. `workspaces`

```sql
CREATE TABLE workspaces (
    id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name        VARCHAR(64) NOT NULL,
    -- COLLATE "C": a slug is an identifier, not prose. (D-40)
    slug        VARCHAR(64) COLLATE "C" NOT NULL UNIQUE,
    avatar_url  TEXT,

    -- Audit only. Ownership is workspace_members.role = 'owner'. (D-22)
    created_by  UUID REFERENCES users(id) ON DELETE SET NULL,

    -- Self-hosters pay for the disk, so uploads are capped per workspace. (D-16)
    storage_quota_bytes BIGINT NOT NULL DEFAULT 5368709120,  -- 5 GiB
    storage_used_bytes  BIGINT NOT NULL DEFAULT 0,

    -- NULL means infinite, which is the default and the product's tenet: nothing is
    -- thrown away. An operator opts in; the purge job (D-30) enforces it. (D-27)
    retention_days      INTEGER,

    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    -- When an owner asked for it to be deleted: from then it is no workspace to anybody (the tenancy
    -- guard refuses it), and NULL again if an owner takes it back within the grace period. (D-242)
    deleted_at  TIMESTAMPTZ,
    -- When `purge:workspaces` claimed it, under the row's lock: past this, nobody can take it back. (0071)
    purge_started_at TIMESTAMPTZ,
    -- When its content was gone. The row stays, a tombstone with its name, for the trails that refer
    -- to it (I-9). (0071)
    purged_at   TIMESTAMPTZ,

    CONSTRAINT storage_used_non_negative CHECK (storage_used_bytes >= 0),

    -- Claimed only once asked for, purged only once claimed. (0071)
    CONSTRAINT workspaces_deletion_order CHECK (
        (purge_started_at IS NULL OR deleted_at IS NOT NULL)
        AND (purged_at IS NULL OR purge_started_at IS NOT NULL)
    ),

    -- A floor, not a preference. A typo of `1` in a retention field would delete a
    -- team's memory overnight and no correct value is that small. (D-27)
    CONSTRAINT retention_days_sane
        CHECK (retention_days IS NULL OR retention_days >= 30)
);

-- No index on `slug`: the UNIQUE constraint above already is one, and a second, partial one
-- only made every write to this table pay twice. Dropped by 0009. (D-89)

-- The foreign key's index (see §6.2).
CREATE INDEX idx_workspaces_created_by ON workspaces (created_by) WHERE created_by IS NOT NULL;
```

### 4.3. `workspace_invitations`

The links that let a person in (D-115). Only the token's digest is kept, as a session's is; a link is
revoked by setting `revoked_at`, never by deleting the row, which stays the record of what was handed
out. Who joined by which link is in `audit_log` (`member.joined`, `metadata.invitationId`), so a join
writes no counter here.

```sql
CREATE TABLE workspace_invitations (
    id            UUID PRIMARY KEY,
    workspace_id  UUID NOT NULL REFERENCES workspaces(id) ON DELETE RESTRICT,
    token_hash    TEXT NOT NULL UNIQUE,
    created_by    UUID REFERENCES users(id) ON DELETE SET NULL,
    created_at    TIMESTAMPTZ NOT NULL,
    expires_at    TIMESTAMPTZ NOT NULL,
    revoked_at    TIMESTAMPTZ,

    CONSTRAINT workspace_invitations_id_is_uuidv7
        CHECK (id::text ~ '^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$'),
    CONSTRAINT workspace_invitations_token_is_a_digest CHECK (token_hash ~ '^[0-9a-f]{64}$'),
    CONSTRAINT workspace_invitations_expire_after_made CHECK (expires_at > created_at)
);

CREATE INDEX idx_workspace_invitations_workspace ON workspace_invitations (workspace_id, id DESC);
CREATE INDEX idx_workspace_invitations_created_by ON workspace_invitations (created_by)
    WHERE created_by IS NOT NULL;
```

## 5. Channels

### 5.1. `channels`

Public channels, private channels and DMs share one table. What separates them is `type`, and
two CHECK constraints keep each shape honest. (D-6)

```sql
CREATE TABLE channels (
    id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    workspace_id UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,

    -- NULL for DMs, which are identified by their members, not by a name.
    -- COLLATE "C" so that lower(name) folds identically on every deployment: under a Turkish
    -- locale lower('İ') does not produce 'i', and channel-name uniqueness would otherwise
    -- depend on how the server was provisioned. (D-40)
    name         VARCHAR(64) COLLATE "C",
    topic        TEXT,
    type         channel_type NOT NULL DEFAULT 'public',

    -- Sorted, colon-joined user UUIDs of the conversation's people (two, or up to ten for a
    -- group, D-127). Set only for DMs; the partial unique index below uses it to stop a second
    -- conversation opening between the same people.
    dm_key       TEXT,

    created_by   UUID REFERENCES users(id) ON DELETE SET NULL,

    -- Denormalized so the sidebar can order channels without touching `messages`.
    last_message_at TIMESTAMPTZ,

    -- The channel's own count of its renames and changes of who posts, raised in the statement that
    -- makes one under the row lock: `CHANNEL_UPDATED` carries it and a client drops an older one
    -- (0023, D-123, D-243).
    state_version INTEGER NOT NULL DEFAULT 0,

    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    -- Archived (D-123): hidden from everyone, its messages and memberships kept, its name free.
    deleted_at   TIMESTAMPTZ,

    -- How long the channel keeps its history when that is longer than its workspace does (D-225).
    -- `min_retention_days`: at least this many whole days, whatever the workspace's window; NULL is no
    -- floor of its own. `retain_forever`: everything. NULL and false — every channel until an owner
    -- says otherwise — is the workspace's window. The purge keeps the longer of the two (I-10). (0063)
    min_retention_days INTEGER,
    retain_forever     BOOLEAN NOT NULL DEFAULT FALSE,

    -- Only the workspace's owners and admins post a root here (D-243): an announcement channel. A
    -- reply in a thread, an edit and a GitHub feed's event are not held to it. (0072)
    only_admins_post   BOOLEAN NOT NULL DEFAULT FALSE,

    CONSTRAINT named_unless_dm CHECK (
        (type = 'direct_message' AND name IS NULL)
        OR (type <> 'direct_message' AND name IS NOT NULL)
    ),
    CONSTRAINT dm_key_iff_dm CHECK (
        (type = 'direct_message') = (dm_key IS NOT NULL)
    ),

    -- The workspace's own floor (`retention_days_sane`); a number of days or forever, never both; and
    -- none of it on a direct message, which nobody configures (D-225). "Never shorter than the
    -- workspace" compares two rows and is not a CHECK: the service refuses it, and the purge takes the
    -- longer window whatever is stored (I-10).
    CONSTRAINT channels_retention_sane CHECK (
        (min_retention_days IS NULL OR min_retention_days >= 30)
        AND NOT (retain_forever AND min_retention_days IS NOT NULL)
        AND (type <> 'direct_message' OR (min_retention_days IS NULL AND NOT retain_forever))
    ),

    -- A direct message is its people, and nobody configures it (D-123, D-243).
    CONSTRAINT channels_only_admins_post_not_dm CHECK (
        type <> 'direct_message' OR NOT only_admins_post
    ),

    -- Two lower-case member ids, the first not above the second byte-wise, joined with ':'.
    -- Added by 0010 for two people, replaced by 0025 for two to ten (a group conversation, D-127);
    -- each NOT VALID then validated. Two ids may be equal (a note to self); three or more are
    -- strictly ascending, `member_key_is_sorted` comparing them byte for byte. (I-5, D-90)
    CONSTRAINT dm_key_form CHECK (dm_key IS NULL
        OR (dm_key ~ '^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}(:[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}){1,9}$'
            AND public.member_key_is_sorted(dm_key))),

    -- The target of the composite keys below: a message names its channel *and* the
    -- channel's workspace, and the database checks that they belong together. (D-90)
    CONSTRAINT channels_id_workspace_id_key UNIQUE (id, workspace_id)
);

-- Channel names are unique per workspace, case-insensitively, and only among
-- live named channels. Deleting #api frees the name for reuse.
CREATE UNIQUE INDEX idx_channels_unique_name
    ON channels (workspace_id, lower(name))
    WHERE type <> 'direct_message' AND deleted_at IS NULL;

-- One DM per pair per workspace.
CREATE UNIQUE INDEX idx_channels_unique_dm
    ON channels (workspace_id, dm_key)
    WHERE type = 'direct_message';

-- Deliberately not ordered by last_message_at: every send writes that column, and a column
-- in an index cannot be changed by a heap-only update. The sidebar sorts what this finds. Not
-- partial, because it is also the index the foreign key to workspaces needs. (D-88)
CREATE INDEX idx_channels_workspace
    ON channels (workspace_id);

-- The foreign key's index (see §6.2).
CREATE INDEX idx_channels_created_by ON channels (created_by) WHERE created_by IS NOT NULL;
```

`last_message_at` is only ever moved forward, and only by a send that is newer than the value it holds; a
send that is not the newest writes nothing. It is the one column of this table that changes on the hot
path, which is why it is in no index. (D-88)

`min_retention_days` and `retain_forever` are an owner's, set through `PUT /api/channels/:channelId/retention`
(D-225), and only ever lengthen what the channel keeps: a floor shorter than the workspace's window is refused
when it is set, and a workspace window lengthened past it later simply wins — the purge keeps the longer of the
two, read on every batch. An archived channel keeps its setting, and the purge still applies it: archiving
hides a channel, it does not change how long its history is kept (D-123).

`only_admins_post` is an owner's or an admin's, set through `PATCH /api/channels/:channelId` (D-243). A send
reads it by the channel's primary key, and only for a root: a reply never reads it.

### 5.2. `channel_members`

Membership, read position, unread counters and per-channel notification level.

```sql
CREATE TABLE channel_members (
    id         UUID NOT NULL PRIMARY KEY DEFAULT gen_random_uuid(),
    channel_id UUID NOT NULL REFERENCES channels(id) ON DELETE CASCADE,
    user_id    UUID NOT NULL REFERENCES users(id)    ON DELETE CASCADE,

    last_read_message_id UUID,

    -- N+1 the project rules forbid. (D-13)
    unread_count         INTEGER NOT NULL DEFAULT 0,
    unread_mention_count INTEGER NOT NULL DEFAULT 0,

    -- a frame that is not newer than the one it holds. Added by 0015. (D-99, amended)
    state_version        INTEGER NOT NULL DEFAULT 0,

    -- Defaults to 'mentions': quiet by default is the product, not a preference. (D-12)
    notification_level notification_level NOT NULL DEFAULT 'mentions',

    starred_at TIMESTAMPTZ,

    UNIQUE (channel_id, user_id),
    CONSTRAINT unread_counts_non_negative
        CHECK (unread_count >= 0 AND unread_mention_count >= 0),

    -- I-6. What needs you is, first, something you have not read. Added by 0013, NOT VALID
    -- then validated, once the service that defines a counted mention existed. (D-99)
    CONSTRAINT unread_mention_within_unread
        CHECK (unread_mention_count <= unread_count),

    -- I-3. SET NULL names its column: the plain form would also null `channel_id`, which a
    -- membership cannot exist without. Added by 0010, NOT VALID then validated. (D-90)
    CONSTRAINT channel_members_last_read_channel_fkey
        FOREIGN KEY (last_read_message_id, channel_id) REFERENCES messages (id, channel_id)
        ON DELETE SET NULL (last_read_message_id)
);

CREATE INDEX idx_channel_members_user ON channel_members (user_id);

-- Deleting a message asks which memberships last read it (ON DELETE SET NULL). (D-89)
CREATE INDEX idx_channel_members_last_read
    ON channel_members (last_read_message_id) WHERE last_read_message_id IS NOT NULL;
```

> `channels`. The migration therefore creates `channels`, then `messages`, then
> `channel_members` — or adds the `last_read_message_id` foreign key in a later statement.

## 6. Messages & Threads

### 6.1. `messages`

The hot table. Everything about it is shaped by read patterns.

```sql
CREATE TABLE messages (
    -- No DEFAULT: the application supplies a UUIDv7. An insert that forgets one
    -- fails loudly instead of silently creating an unorderable row. (D-8)
    id           UUID PRIMARY KEY,

    workspace_id UUID NOT NULL REFERENCES workspaces(id) ON DELETE CASCADE,

    -- Keyed together with workspace_id below: a message is in the workspace of its channel.
    channel_id   UUID NOT NULL,

    -- RESTRICT, because users are soft-deleted and authorship must survive. (D-22)
    -- NULL for a message nobody wrote: a repository's event (`messages_sender_by_type`, 0032, D-134), or an
    -- incoming webhook's post (0074, D-245).
    sender_id    UUID REFERENCES users(id) ON DELETE RESTRICT,

    -- Threads are exactly two levels deep: a root message and its replies.
    -- A reply may not itself be a parent. Enforced in the message service.
    -- Keyed together with channel_id below: a reply is in its parent's channel.
    parent_id    UUID,

    -- Denormalized thread summary, so rendering a feed of 50 root messages
    -- does not become 50 extra queries.
    thread_reply_count   INTEGER NOT NULL DEFAULT 0,
    thread_last_reply_at TIMESTAMPTZ,

    -- Counts changes to the thread summary, the reaction set and the content (an edit, D-103),
    -- in the statement that makes them, so versions are in commit order; `THREAD_UPDATED` and
    -- `REACTIONS_UPDATED` carry it. Added by 0015. (D-99, amended)
    state_version        INTEGER NOT NULL DEFAULT 0,

    -- The wedge: a thread can be closed, and stays searchable. (D-2)
    resolved_at  TIMESTAMPTZ,
    resolved_by  UUID REFERENCES users(id) ON DELETE SET NULL,
    is_question BOOLEAN NOT NULL DEFAULT FALSE,
    question_assignee_id UUID REFERENCES users(id) ON DELETE SET NULL,
    accepted_answer_id UUID REFERENCES messages(id) ON DELETE SET NULL,
    decision_note TEXT NOT NULL DEFAULT '',
    decision_url TEXT,
    decision_updated_by UUID REFERENCES users(id) ON DELETE SET NULL,
    knowledge_version INTEGER NOT NULL DEFAULT 0,
    CONSTRAINT messages_knowledge_root CHECK (parent_id IS NULL OR (NOT is_question AND question_assignee_id IS NULL AND accepted_answer_id IS NULL AND decision_note = '' AND decision_url IS NULL AND knowledge_version = 0)),
    CONSTRAINT messages_decision_note_length CHECK (char_length(decision_note) <= 2000),
    CONSTRAINT messages_decision_url_length CHECK (char_length(decision_url) <= 2048),
    CONSTRAINT messages_knowledge_version CHECK (knowledge_version >= 0),
    CONSTRAINT messages_question_assignee CHECK (question_assignee_id IS NULL OR is_question),
    CONSTRAINT messages_answer_not_self CHECK (accepted_answer_id IS NULL OR accepted_answer_id <> id),

    content      TEXT NOT NULL,
    message_type message_type NOT NULL DEFAULT 'text',

    -- Renderer hints and system-event payloads, read by `message_type`, never by their shape: a
    -- `text` message's `TextMetadata`, a `system_event`'s `GitHubEvent` ('{}' once it is a
    -- tombstone). Never used for tenant filtering.
    metadata     JSONB NOT NULL DEFAULT '{}'::jsonb,

    edited_at    TIMESTAMPTZ,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at   TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    deleted_at   TIMESTAMPTZ,

    -- When the server last wrote the row, to the millisecond, on the database's clock: stamped by the
    -- `messages_stamp_changed_at` trigger on every UPDATE (left alone when a statement sets it) and by
    -- the default on insert. What a client that was away asks by; never an id's order. Added by 0058. (D-194)
    changed_at   TIMESTAMPTZ NOT NULL DEFAULT date_trunc('milliseconds', clock_timestamp()),

    -- A person's message has its sender; an event has none. Added by 0032. (D-134 §6)
    CONSTRAINT messages_sender_by_type CHECK ((message_type = 'text') = (sender_id IS NOT NULL)),
    -- An event's metadata names a kind the contract knows, or is '{}' as a tombstone. Added by 0032;
    -- 0074 adds an incoming webhook's post, `{ kind: 'incoming_webhook', name }` (D-245).
    CONSTRAINT messages_event_known CHECK (
        message_type = 'text'
        OR metadata = '{}'::jsonb
        OR metadata ->> 'kind' IN ('push', 'pull_request', 'issues', 'release', 'incoming_webhook')
    ),

    -- Only root messages are resolvable; resolving a reply is meaningless.
    CONSTRAINT only_roots_resolve CHECK (parent_id IS NULL OR resolved_at IS NULL),

    -- Resolution is all-or-nothing: never a timestamp without an actor.
    CONSTRAINT resolution_is_complete
        CHECK ((resolved_at IS NULL) = (resolved_by IS NULL)),

    -- Replies have no thread summary of their own.
    CONSTRAINT replies_have_no_thread_summary
        CHECK (parent_id IS NULL OR thread_reply_count = 0),

    CONSTRAINT thread_reply_count_non_negative CHECK (thread_reply_count >= 0),

    -- The contract's MESSAGE_CONTENT_MAX, for every writer that is not one of the
    -- two doors, in UTF-16 code units as the contract counts them: characters, plus one more
    -- for each outside the Basic Multilingual Plane. Added by 0007 as characters and replaced
    -- by 0011 with the units. (D-67, D-86)
    CONSTRAINT messages_content_length CHECK (
        char_length(content)
        + char_length(regexp_replace(content, '[^\U00010000-\U0010FFFF]', '', 'g'))
        <= 16000
    ),

    -- Version 7 and the RFC variant: the contract's isMessageIdShape, for a writer that skips it.
    -- The timestamp inside is not checked here (a CHECK must be immutable); the service does. (D-8, D-33, D-90)
    CONSTRAINT messages_id_is_uuidv7
        CHECK (id::text ~ '^[0-9a-f]{8}-[0-9a-f]{4}-7[0-9a-f]{3}-[89ab][0-9a-f]{3}-[0-9a-f]{12}$'),

    -- The tenant keys, added by 0010 (NOT VALID, then validated). Each contains, and so replaces,
    -- the single-column key it was written beside. (I-1 in part, I-3, I-4, D-90)
    CONSTRAINT messages_id_channel_id_key UNIQUE (id, channel_id),
    -- The target of an attachment's key: it is in its message's workspace (0018, D-109).
    CONSTRAINT messages_id_workspace_id_key UNIQUE (id, workspace_id),
    CONSTRAINT messages_channel_workspace_fkey
        FOREIGN KEY (channel_id, workspace_id) REFERENCES channels (id, workspace_id)
        ON DELETE CASCADE,
    CONSTRAINT messages_parent_channel_fkey
        FOREIGN KEY (parent_id, channel_id) REFERENCES messages (id, channel_id)
        ON DELETE RESTRICT
);
```

### 6.2. Indexes

```sql
-- Primary feed. Keyset pagination on `id` alone: UUIDv7 is byte-wise time-ordered,
-- and PostgreSQL compares the uuid type byte-wise, so this index IS chronological.
-- Root messages only, because thread replies are read with their root, in its thread (D-8, D-122).
-- A deleted root with replies keeps its place, as its tombstone (D-103 §7). Redefined by 0016.
CREATE INDEX idx_messages_channel_feed
    ON messages (channel_id, id DESC)
    WHERE parent_id IS NULL AND (deleted_at IS NULL OR thread_reply_count > 0);

-- Expanding one thread: every reply, a deleted one as its tombstone (D-103 §7). Redefined by 0016.
CREATE INDEX idx_messages_thread
    ON messages (parent_id, id)
    WHERE parent_id IS NOT NULL;

-- Scoped substring / identifier search. btree_gin lets workspace_id sit inside the
-- GIN index, so the trigram scan is confined to one tenant instead of the whole table. (D-10)
-- On the folded text, which search compares: case ignored by Unicode, I ı İ i one letter
-- (0043, D-105 §1 amended, #700). It replaced idx_messages_search, on the raw content.
CREATE FUNCTION purlay_fold(value text) RETURNS text
    LANGUAGE sql IMMUTABLE STRICT PARALLEL SAFE
    RETURN translate(lower(value COLLATE "und-x-icu"), 'ı' || U&'\0307', 'i') COLLATE "C";

CREATE INDEX idx_messages_search_folded
    ON messages USING gin (workspace_id, purlay_fold(content) gin_trgm_ops)
    WHERE deleted_at IS NULL;

-- "Messages by this user", and the guard against orphaned RESTRICT references.
CREATE INDEX idx_messages_sender ON messages (sender_id);

-- Open questions across a workspace: the resolvable-thread feature's own view.
-- Only roots that have a reply: nearly every root has none, and an index of all of them made
-- a view that wants the rare ones read them all (6,975 buffers against 41 on 400,000 messages).
-- Redefined by 0014.
CREATE INDEX idx_messages_unresolved
    ON messages (workspace_id, id DESC)
    WHERE parent_id IS NULL AND resolved_at IS NULL AND deleted_at IS NULL
      AND thread_reply_count > 0;

-- The foreign keys. The indexes above are partial, and the query that enforces a foreign key
-- filters on the column alone, so none of them can answer it. Without these, deleting 100 of
-- 1,000,000 messages took 4.9 s and deleting a channel did not finish in 60 s. (D-89)
-- What a client catching up reads: one channel in the order things happened to it (D-194). Added by 0058,
-- which dropped `idx_messages_channel (channel_id)`: this one leads with the same column, so it serves the
-- foreign key too.
CREATE INDEX idx_messages_changes     ON messages (channel_id, changed_at, id);
CREATE INDEX idx_messages_parent      ON messages (parent_id)   WHERE parent_id IS NOT NULL;
CREATE INDEX idx_messages_resolved_by ON messages (resolved_by) WHERE resolved_by IS NOT NULL;
CREATE INDEX idx_messages_questions ON messages (workspace_id, id) WHERE is_question AND resolved_at IS NULL AND deleted_at IS NULL;
CREATE INDEX idx_messages_question_assignee ON messages (question_assignee_id, id) WHERE question_assignee_id IS NOT NULL;
CREATE INDEX idx_messages_accepted_answer ON messages (accepted_answer_id) WHERE accepted_answer_id IS NOT NULL;
CREATE INDEX idx_messages_decision_author ON messages (decision_updated_by) WHERE decision_updated_by IS NOT NULL;

-- The retention purge's read: one workspace's messages older than its window, from the oldest
-- (D-139 §1). By workspace alone, a night would walk the workspace's whole history once a batch.
-- Added by 0039, which dropped `idx_messages_workspace (workspace_id)`: this one leads with the same
-- column, so it serves the foreign key too.
CREATE INDEX idx_messages_workspace_age ON messages (workspace_id, created_at);
```

**Every foreign key column leads an index the planner can use for it**, and a test reads the catalogue to
prove it, so a table added later cannot forget one. A nullable column is indexed only where it is set,
which is all a lookup by value needs. Measured on 1,000,000 messages (10 workspaces, 200 channels,
200 users):

| | before | after |
|---|---|---|
| `DELETE` of 100 messages | 4,756 ms | 8.7 ms |
| `DELETE` of one channel (5,000 messages, cascading) | did not finish in 60 s | 90 ms |
| the four new `messages` indexes, on disk | | 14 MB over 376 MB of indexes |
| 20,000 single-row inserts | 1,107 ms | 1,168 ms (+5 %) |

**The search index is the expensive one, and it stays.** `idx_messages_search` (now `idx_messages_search_folded`, on the folded text — #700) was 206 MB of the 376 MB the
table's indexes occupy, and removing it made 20,000 single-row inserts 1.8 times as fast on
high-entropy text (1,107 ms against 613 ms) and 1.45 to 1.6 times on prose (892 and 1,036 ms against 607
and 651). That is about 15 to 25 µs a message, which is invisible at the rate a team sends and is the price
of substring search (D-10) without a second system. It is written down so that it is a choice: it is
reopened when insert latency shows up in a measurement of the send path, or when search moves out of
the database.

### 6.3. Pagination Contract

```sql
-- Newest page
SELECT * FROM messages
 WHERE channel_id = $1 AND parent_id IS NULL AND deleted_at IS NULL
 ORDER BY id DESC
 LIMIT 50;

-- Older page: the cursor is the last id seen. No timestamp, no offset, no tie-break.
SELECT * FROM messages
 WHERE channel_id = $1 AND parent_id IS NULL AND deleted_at IS NULL
   AND id < $2
 ORDER BY id DESC
 LIMIT 50;
```

`OFFSET` is prohibited on this table: it is O(n) and shifts under concurrent inserts, which in
a live channel is *every* page.

0036 also widens the timeline: `incident_updates_kind_known` takes `responder_added` and

> The incident and its timeline entry are written in one transaction, the incident's row locked for a
> change. The timeline is never updated; it goes with its incident, which goes with its channel. The
> channel list reads the open one's severity and status through the open index, a join and not a
> query a channel. Every foreign key is indexed (D-89). A direct message has no incident: the service
> refuses one (`404`), the table does not — a channel's type is not on this row, and holding it here
> would take a trigger; accepted, as the service is the one writer.

> `INCOMING_WEBHOOKS_PER_CHANNEL_MAX` a channel, counted under the channel's row lock. Revoking deletes the row:
> a post racing it waits on the row lock its `last_used_at` takes, and finds nothing. What a hook posted is a
> `system_event` whose metadata keeps the name it posted under (`messages_event_known`), so a hook revoked or
> renamed since still names what it said. Never exported (D-245).

### 8.4. The GitHub App (D-246)

The server's App is a row of `server_settings` (§9.5). What belongs to a workspace or a person is here, read and
written by `modules/integrations/github-app*.ts`.

- **`github_app_installations`** — at most one installation per workspace, connected by an owner. GitHub's
  `installation_id` is **not** unique: two workspaces of one organisation may both connect it, so it is indexed for
  the deliveries that name it, not constrained. It goes with its workspace; `connected_by` outlives its person as
  NULL. `suspended_at` is GitHub's word, kept as said.
- **`github_user_authorizations`** — a person's own App user access token and its refresh token, **one per
  person**, never a workspace's. Both sealed by the one cipher with the row's id and the column bound in
  (D-39 §6); never logged, returned or exported. The expiries are GitHub's (an App whose tokens do not expire
  leaves them NULL); an expiry belongs to a refresh token. `github_user_id` finds the row when GitHub says that
  person revoked the App.
- **`github_app_handshakes`** — a trip to GitHub and back, by the digest of its `state` (only the digest is kept),
  ten minutes long and spent on return. An `install` is a workspace's and has no verifier; an `authorize` is a
  person's and carries its PKCE verifier, sealed.
- **`github_app_deliveries`** — each delivery to the App's one address, recorded in the transaction that applies it:
  its id, and its body's digest, each unique, so a redelivery or a signed body under a made-up id applies nothing
  (D-134 §5, D-231 §1). Swept after thirty days.

```sql
CREATE TABLE github_app_installations (

    CONSTRAINT github_app_installations_account_type_known
        CHECK (account_type IN ('User', 'Organization'))
);

CREATE INDEX idx_github_app_installations_installation
    ON github_app_installations (installation_id);
CREATE INDEX idx_github_app_installations_connected_by
    ON github_app_installations (connected_by) WHERE connected_by IS NOT NULL;

CREATE TABLE github_user_authorizations (
    id                      UUID PRIMARY KEY,
    user_id                 UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    github_user_id          BIGINT NOT NULL,

    access_expires_at       TIMESTAMPTZ,

CREATE INDEX idx_github_user_authorizations_github_user
    ON github_user_authorizations (github_user_id);

CREATE TABLE github_app_handshakes (
    state_digest       TEXT COLLATE "C" PRIMARY KEY,
```

### 8.5. `github_links` and `github_operations` (D-246)

- **`github_links`** — a root linked to an issue or a pull request, made from the thread or pointed at: the
  repository by its number and its name, the title and state as GitHub last said them, and `state_at`, GitHub's own
  instant, so a delivery that arrives out of order cannot move it back. Channel-scoped (the composite key every
  channel row has), `ON DELETE CASCADE` from the root; exported with the workspace (D-140), never in a person's
  own. A link outlives the installation that found it: a record, not a permission.
- **`github_operations`** — the bounded record of one attempt to make an issue, keyed by workspace, actor and the
  client's request id. `content_digest` is a SHA-256 of what was asked, never the words; `marker` is the line
  the issue ends with, by which a lost answer is found again; `status` is `pending`, `created` (with its issue
  number), `unknown` or `refused` (with a closed reason). Swept thirty days after its last change; never exported.

### 9.1. `audit_log`

Append-only. The application role holds `INSERT` on this table and nothing else; a test asserts
no service issues `UPDATE` or `DELETE` against it. (D-26)


### 9.1a. `server_audit_log`

The trail of changes to the server's own settings (Administration → Server, D-179 §4.8). `audit_log`
is a workspace's, with its workspace required; the server's settings belong to none, so they have a
trail of their own, append-only on the same terms (I-9). It says who, which setting and when — the
action names both (`server.github_connected`, `server.github_disconnected`, `server.smtp_connected`,

### 9.4. `object_deletions`

### 9.5. `server_settings`

The operator's settings for the whole server (D-179 §6): who may sign up, GitHub's OAuth app, the mail
relay, who may make a workspace (D-155, D-169), the sign-in policy (D-239) and how long a session lives (D-244). They are in the database because a person changes
them in the browser; what the process needs before it can read a row — the database, `ENCRYPTION_KEY`,
the storage, `APP_URL`, where GitHub is — stays in the environment (`CONFIG.md`).

- **One row.** The key is a boolean that can only be `TRUE`, so a second row is refused by the primary
  key rather than by every reader agreeing to take the first. Typed columns rather than key/value rows:
  each setting has a type, a default and a check here, and a reader of a missing one fails to compile.
- **The secrets are sealed by the application** — the GitHub client secret, and the whole SMTP address,
  which carries the relay's password — by the one credential cipher (D-39 §6), with the column's name
  as the additional data: a ciphertext copied into the other column does not open there. They are never
  logged, never exported (`EXCLUDED` in `modules/export/tables.ts`) and never in a response, whose view
  says only whether each is set (`settingsView` in `modules/setup/settings.ts`).
- **Pairs are pairs**: a client id with its secret, a relay with its sender, or neither. The single
  sign-on provider (D-200, added by 0059) is a triple — issuer, client id and sealed client secret — or
  none; its optional `oidc_name` labels the sign-in button and needs a provider. The issuer is kept as
  written, never normalised: the id_token's `iss` must equal it byte for byte.
- **Who may make a workspace** is D-155's rule as a kind — `first`, `anyone` or `listed` — and, for
  `listed`, the GitHub logins in lower case, at least one.
- **The sign-in policy** (D-239, added by 0068): `require_two_factor` holds an account that signs in with a
  password back until it turns on two-step verification, and `password_sign_in` is whether a password signs
  in at all. Off is allowed only while GitHub or single sign-on is connected, and the last of them is not
  disconnected while it is — a rule the application weighs inside the transaction that saves the change, not
  a check here: a provider whose secret a rotated key cannot open is set in its columns and no way in, which
  only the application can tell. `bun run admin:reset-password` turns passwords on again.
- **How long a session lives** (D-244, added by 0073): `session_idle_timeout_hours` signs out a session unused for
  that long, and `session_max_age_days` one that old since its sign-in, whatever its use; `NULL` is off, as every
  server was before. Which values may be chosen is `@purlay/types`' (`SESSION_IDLE_TIMEOUT_HOURS`,
  `SESSION_MAX_AGE_DAYS`); the check here refuses only what no policy could mean. Nothing is written into
  `sessions` (§3.2): each session is judged from its own `created_at` and `last_used_at` when it is read, so a
  change reaches the sessions already open.
- `imported_from_env_at` is when the environment was copied in, **once**, on the first start; set, every
  later start leaves the row alone (`importFromEnvOnce`). `setup_completed_at` is when the setup in the
  browser was finished.

Instance-wide, like `job_runs`: an operator's table, holding nothing of anybody.

```sql
CREATE TABLE server_settings (
    id                        BOOLEAN PRIMARY KEY DEFAULT TRUE,
    sign_up                   TEXT NOT NULL DEFAULT 'invite-only',
    github_client_id          TEXT,
    -- Sealed, base64, bound to this column's name.
    github_client_secret_encrypted TEXT,
    -- Sealed, base64, as above: the whole smtp:// or smtps:// address, credentials and all.
    smtp_url_encrypted        TEXT,
    mail_from                 TEXT,
    smtp_allow_plaintext      BOOLEAN NOT NULL DEFAULT FALSE,
    workspace_creators        TEXT NOT NULL DEFAULT 'first',
```

### 9.6. `setup_state`

Where the setup in the browser stands (D-179 §4): the one-time code, the throttle on guessing it, the
browser the setup is bound to, and how far it has come. Whether setup is **finished** is not here — that
is `server_settings.setup_completed_at` (§9.5), its one home. Read and written by
`modules/setup/setup.ts` alone.

- **One row**, held to one by its key as `server_settings` is, and made by the migration itself, so
  every reader can lock it (`FOR UPDATE`) and none has to make it first.
- **Digests only**, SHA-256 in hex (`platform/tokens.ts`): `code_digest` of the setup code and
  `claim_digest` of the claim token. The code is written once, to the log of the start that issued it;
  the token is handed to the browser once. A claim spends the code, clearing both its columns.
- A code opens for an hour from `code_issued_at`.
- **The throttle is the server's**: `failed_attempts` counts every wrong code, whoever sent it, and the
  fifth sets `locked_until` fifteen minutes on and starts the count again; a claim made starts it again
  too. Both belong to the code: a new code, at a start, clears them.
- **The claim** — `claim_digest`, `claimed_at`, `claimed_by` (the browser's id, as the route names it)
  and `claim_seen_at` — is all set or all empty. One whose browser has not been seen for a day no longer
  opens; a code from a later start replaces one unseen for fifteen minutes (D-179 §4.2).
- `admin_user_id` is the administrator an unfinished setup made: a server with any other user is closed
  to setup. Finishing clears it, so afterwards every user keeps setup closed.
- `step_reached` is the last step passed, of the closed set `SETUP_STEPS` in `@purlay/types`; steps are
  passed in order, so it says which are passed whole. `finish` is written only with
  `server_settings.setup_completed_at`, by the finish, which spends the claim — the one step a claim
  does not hold.
- `github_tried_at` and `email_tried_at` (migration 0052): when the setup saved a GitHub app GitHub's
  token endpoint accepted, and a relay that took the administrator's test letter. The finish rule counts
  only these (D-179 §4.5) — an app or a relay merely in the settings was never tried. Facts about what
  was saved, not about a claim: a claim taken over keeps them.

Instance-wide, like `server_settings`; never exported.

```sql
CREATE TABLE setup_state (

    code_digest       TEXT,
    code_issued_at    TIMESTAMPTZ,
    failed_attempts   INTEGER NOT NULL DEFAULT 0,
    locked_until      TIMESTAMPTZ,
    claim_digest      TEXT,
    claimed_at        TIMESTAMPTZ,
    claimed_by        TEXT,
    claim_seen_at     TIMESTAMPTZ,
    admin_user_id     UUID REFERENCES users(id) ON DELETE SET NULL,
    step_reached      TEXT,
    step_reached_at   TIMESTAMPTZ,
    github_tried_at   TIMESTAMPTZ,
    email_tried_at    TIMESTAMPTZ,

    CONSTRAINT setup_state_one_row CHECK (id),
    CONSTRAINT setup_state_code_digest CHECK (code_digest ~ '^[0-9a-f]{64}$'),
    CONSTRAINT setup_state_code_whole CHECK ((code_digest IS NULL) = (code_issued_at IS NULL)),
    CONSTRAINT setup_state_failed_attempts CHECK (failed_attempts >= 0),
    CONSTRAINT setup_state_claim_digest CHECK (claim_digest ~ '^[0-9a-f]{64}$'),
    CONSTRAINT setup_state_claimed_by CHECK (char_length(claimed_by) BETWEEN 1 AND 128),
    CONSTRAINT setup_state_claim_whole CHECK (
        (claim_digest IS NULL) = (claimed_at IS NULL)
        AND (claim_digest IS NULL) = (claimed_by IS NULL)
        AND (claim_digest IS NULL) = (claim_seen_at IS NULL)
    ),
    CONSTRAINT setup_state_step CHECK (step_reached IN (
```

### 9.7. `admin_email_verification`

The setup administrator's own address check (D-179 §4.3, Ruling R32): the one link the wizard mails to
the administrator, whose following sets `users.email_verified` — never the sign-in library's magic link,
which on an account whose address was never proven removes its password. Read and written by
`modules/setup/verification.ts` alone.

- **One row at most**, held to one by its key as `setup_state` is: setup makes one administrator, and a
  new link replaces the one before it (an upsert on the key).
- **A table of its own, not columns of `setup_state`**: the letter can be opened after the finish, which
  clears `setup_state.admin_user_id` and spends the claim, so the row names its account itself
  (`user_id`) and following the link needs neither.
- **A digest only**, SHA-256 in hex (`platform/tokens.ts`): the token is mailed once, in the link's
  fragment (`/setup/verify#<token>`).
- **Bound to the address it was mailed to** (`email`, as `users.email` held it): a link followed after
  the account's address changed verifies nothing.
- A link opens for a day from `issued_at`; following it deletes the row, in the transaction that sets
  `users.email_verified` — and only the click whose delete removed it may set it. A row past its day is
  deleted when it is tried, and by `sweep:email-sign-ins`.
- `ON DELETE CASCADE` for an account's row deleted; erasure, which keeps the row under an anonymised
  account (D-139 §5), deletes it by `user_id`.

Instance-wide, like `setup_state`; never exported.

### 9.8. `invitation_passports`

What lets a newcomer make an account on an invite-only server by an invitation link (D-179 §5, Ruling
R51): a passport made from a live link and spent by the one sign-up it was made for. Read and written by
`modules/workspaces/invitation-passport.ts`; spent from `databaseHooks.user.create.before`
(`modules/auth/better-auth.ts`).

- **Two kinds**: `github` holds `cookie_digest`, `email` holds `address_digest`, and neither holds the other's
  (a CHECK). Both are SHA-256 in hex (`platform/tokens.ts`); the cookie's value and the address are never
  stored. The address is lower-cased and trimmed first (`normalisedMailbox`).
- **An hour, once**: `expires_at`, and `consumed_at` set by the sign-up's own transaction, by an update that
  only one caller can win.
- **As live as its link**: `invitation_id` names the link and every use reads it again (not revoked, not
  expired, its workspace not deleted). `ON DELETE CASCADE` for the day a link is deleted.
- **One passport per address and link**: the unique pair; asking again replaces it. Cookie digests are
  unique.
- A day past its hour or its use the daily sweep deletes the row; erasure deletes an address's `email` rows
  by the digest of the address it read before the tombstone.

Instance-wide; never exported.


### 9.9. `native_authorizations`

What lets the native application sign in without a password of its own (D-191): a one-time code, made while
a person is signed in in a browser and spent by the application that started the flow. Read and written by
`modules/auth/native-handoff.ts`.

- **The code is never stored**: `code_digest` is the SHA-256 of its 64 hex digits (`platform/tokens.ts`), unique.
  A copy of the table spends nothing.
- **Bound to a secret the application keeps**: `challenge` is the base64url SHA-256 of a verifier the
  application made and never sent (43 characters). Spending a code needs the verifier.
- **Two minutes, once**: `expires_at` is two minutes after `created_at` on the server's clock; `spent_at` is set
  by the spend that mints the session, under a lock on the row, so of two at once one wins.
- **Wrong guesses are counted and committed with their refusal**: `wrong_verifiers`, 0 to 5; at five the code is
  burnt (`expires_at` brought to that moment). A wrong guess never burns it earlier.
- **A person's own**: `user_id`, `ON DELETE CASCADE`; at most five live per person, the oldest making room, counted
  under a lock on the person's row.
- A day past its expiry the daily sweep deletes the row; an erasure deletes the person's rows.

Instance-wide; never exported.

```sql
CREATE TABLE native_authorizations (
    id               UUID PRIMARY KEY,
    user_id          UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    code_digest      TEXT NOT NULL,
    challenge        TEXT NOT NULL,
    wrong_verifiers  SMALLINT NOT NULL DEFAULT 0,
    created_at       TIMESTAMPTZ NOT NULL,
    expires_at       TIMESTAMPTZ NOT NULL,
    spent_at         TIMESTAMPTZ,

    CONSTRAINT native_authorizations_code_is_a_digest CHECK (code_digest ~ '^[0-9a-f]{64}$'),
    CONSTRAINT native_authorizations_challenge_is_a_digest CHECK (challenge ~ '^[A-Za-z0-9_-]{43}$'),
    CONSTRAINT native_authorizations_wrong_verifiers_bounded CHECK (wrong_verifiers BETWEEN 0 AND 5),
    CONSTRAINT native_authorizations_lasts CHECK (expires_at >= created_at),
    CONSTRAINT native_authorizations_code_unique UNIQUE (code_digest)
);

CREATE INDEX idx_native_authorizations_user ON native_authorizations (user_id, expires_at);
CREATE INDEX idx_native_authorizations_expiry ON native_authorizations (expires_at);
```

### 9.10. `missed_mail_letters`

## 10. Kysely Types (`packages/db/src/schema.ts`)

**Generated** by `kysely-codegen` from a database with every migration applied, and committed so
that typechecking never needs a running database. The migrations are the single source; the types
are derived, so drift is not detected — it is impossible. CI regenerates and requires an empty
diff. (D-45)

The shape below is what the generator produces once the `CreatedAt`, `UpdatedAt` and `Json<T>`
overrides are configured. It is reproduced here because this document is where the data model is
read, **not** because it is maintained here: editing it by hand is a defect the CI check will
reject.

```typescript
// packages/db/src/schema.ts — generated, never edited
export interface DB {
  users: Users;
  sessions: Sessions;
  workspaces: Workspaces;
  workspace_members: WorkspaceMembers;
  channels: Channels;
  messages: Messages;
  channel_members: ChannelMembers;
  // …one entry per applied migration's tables
}
```

The generator names the root interface `DB`; `@purlay/db` re-exports it as `Database`, which is
the name the rest of the documents use (`ARCHITECTURE.md` §10, D-46). That is an alias, not a
second definition.

**Three things a reader should know, because the generator's output is not obvious:**

- `BIGINT` arrives as a **string**, not a number — `storage_quota_bytes`, `storage_used_bytes` and
  `attachments.size_bytes`. JavaScript's number cannot hold the range, so the driver refuses to
  narrow it.
- **`messages.id` is not `Generated`.** The column has no default, so the generator types it as
  required on insert — which is exactly the loud failure D-8 asked for: an insert that forgets the
  application's UUIDv7 does not compile.
- `JSONB` columns are a `ColumnType` with different read and write shapes: an object on the way
  out, a serialised string on the way in.

A full listing is not reproduced here. It would be a copy of a generated file, and the last
consistency pass spent its time removing exactly that kind of copy. `bun run db:generate`
regenerates it; CI fails on any diff.

## 11. Invariants

Rules the schema cannot express. Each has a named test. (D-21)

| # | Invariant | Enforced in |
|---|---|---|
| I-1 | Threads are at most two levels deep: a reply's `parent_id` must point at a message whose own `parent_id` is `NULL`. The database enforces that a reply is in its parent's channel (and so workspace); depth is the service's. | `messages.service`, in part `messages_parent_channel_fkey` |
| I-2 | Every workspace has at least one live `owner` — an erased one counts for nothing. The last live owner cannot be demoted, removed, or erase their account while another live member remains. | `workspaces/members.ts`, `users/erasure.ts`, under the workspace row's lock (D-111, D-139 §6) |
| I-3 | `channel_members.last_read_message_id` must belong to that channel. | the database: `channel_members_last_read_channel_fkey` |
| I-4 | `messages.workspace_id` must equal the `workspace_id` of its `channel_id`. Denormalized for the tenant guard; must never diverge. | the database: `messages_channel_workspace_fkey` |
| I-5 | `dm_key` is the UUIDs of the conversation's people — two, or up to ten for a group (D-127) — sorted ascending and joined with `:`; the same set is the same conversation. The database enforces the form and the order; that they are people of the workspace is the service's. | `channels.service`, in part `dm_key_form` |
| I-6 | `unread_count` ≥ `unread_mention_count` for every membership row. | the database: `unread_mention_within_unread` (D-99) |
| I-7 | `workspaces.storage_used_bytes` equals the sum of the sizes of the attachments messages carry. Kept by the send that links them; reconciled nightly by `bun run job reconcile:storage`. | `messages.ts` `linkAttachments`, `jobs.ts` `reconcileStorage` |
| I-8 | A resolved thread's root has `parent_id IS NULL` and `thread_reply_count > 0`. | `threads.service` |
| I-9 | `audit_log` is append-only: no service issues `UPDATE` or `DELETE` against it. | `audit/audit.ts`; held by `audit/append-only.test.ts` |
| I-10 | The retention purge deletes nothing when `retention_days IS NULL`, and never a message newer than the window — its channel's window, which is the longer of the workspace's and the channel's own (`channels.retain_forever`, `channels.min_retention_days`), computed on every batch and never taken from a stored number (D-225). Every run writes one `audit_log` entry for each workspace with retention set (D-139 §3). | `modules/retention/purge.ts` |
| I-11 | An erased user has no personal data on `users`, no live session, **no `github_id`**, no `github_login` and no `github_connected_at`, and every message they authored still exists. Erasure never cascades, and a later sign-in creates a new account rather than resurrecting the erased one. (D-27, D-38, D-139 §5, D-176) | `modules/users/erasure.ts` |

**What the database enforces, and what stays with the service.** I-3, I-4 and I-6 are constraints now (the
last with the read-state service, D-99), and I-1 and I-5 are constraints in part (D-90). Four things stay service-level on purpose:

- **Thread depth (I-1, the rest).** A reply's parent must itself be a root. A foreign key cannot say
  "the row I point at has a null column"; it takes a trigger, or a stored generated column on a table of
  millions of rows (a rewrite under an exclusive lock). The tenant half of I-1, that a reply never leaves its
  parent's channel, is the part a leak depends on, and that is in the database.
- **Counters kept equal to other rows (`thread_reply_count`, I-7, I-8).** A maintained count equal to a count
  of other rows is a trigger, and a trigger on the hottest table is a cost this schema has not been shown to
  need. The service maintains them in the send's transaction; a nightly reconcile is the check. A
  `thread_reply_count` of 999 on a message with no replies is accepted by the database, and the audit was
  right to say so.
- **The timestamp inside a message id.** A `CHECK` must be immutable, and "not from the future" is not. The
  service refuses it (D-33); the database refuses a wrong version and variant.
- **That a DM's two ids are members of its workspace**, and that a channel member is a workspace member.
  Neither is a column of the table that holds the pair.
